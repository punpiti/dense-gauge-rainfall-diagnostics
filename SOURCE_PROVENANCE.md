# Source provenance

## Pair-max primary: v1.1.0

`primary/` contains the reviewed pair-max primary and computational controls.
`primary/SOURCE_PROVENANCE.json` records retained source hashes and local
import/data-default adaptations. Numerical functions are unchanged from the
verified manuscript calculations. `primary/SHA256SUMS.json` identifies this
release's calculation files and usage documentation. No restricted inputs,
internal records or separate supplementary-code ZIP are distributed.

The primary/control entrypoint was checked across all 157 retained windows;
matching calculated indicators establishes implementation consistency, not
independent meteorological validation. The requested 120-minute lead is fully
retained in 155 windows; one retains 105 minutes and one none.

## Historical fixed15 provenance

The files under `code/` are byte-for-byte copies, at package build time, of
the corresponding files in the authors' curated paper-processing source tree.

Execution logs retained by the authors confirm that
`build_event_grid_xarray.py`, `compute_optical_flow_xarray.py`, and
`classify_convective_from_residual.py` were executed for the 2026 reviewer
analyses. The 157-storm final label table was generated by
`apply_convective_thresholds.py` in `strict` mode with the manuscript
thresholds, producing 36 and 121 events in the two operational classes.

The source release excludes the internal pipeline runners because those files
mainly manage event-cache creation, repeated execution, directory layout, and
performance. Their exclusion does not replace the method-specific numerical
operations contained in the released scripts.

During the release audit, the default event-sum guide in the surviving
feature-space plotting script was harmonized from a stale development value of
3000 to the final manuscript threshold of 4000. This changes the plotted class
of one storm (`STORM_000193`) and makes the plotting code and regenerated
feature-space figures agree with the released final-label table (36/121).

For a portable one-command demonstration, the optical-flow reader was extended
to accept NetCDF input in addition to the Zarr input used by the Bangkok
pipeline. The Zarr processing path and numerical optical-flow/residual
operations are unchanged. The demo uses NetCDF to avoid Zarr/Dask startup and
filesystem variability in small review environments.

Progress reporting was added to the public demo and to the optical-flow loop.
These changes affect console feedback only and do not change numerical output.

`example/run_pipeline.sh` is a thin command-line hook around the released
paper-processing scripts. Its only required scientific inputs are one rainfall
event-window table and one station-metadata table. It supplies the manuscript
parameters, connects file outputs between stages, and reports their locations;
it performs no scientific calculation. `example/run_demo.sh` differs only by
creating unrestricted synthetic versions of those two inputs before calling
the same hook.
